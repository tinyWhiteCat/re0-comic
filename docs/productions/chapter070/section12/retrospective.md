# 第12节《佛拉基亚帝国》制作复盘

记录日期：2026-11-17，Asia/Shanghai。范围包括第01镜解说、第22镜耳光的多轮返修，以及视频V1至V3的读音、片头、片尾和交付。本页记录可观察的问题与修法，不推测生成服务内部原因。

当前采用分镜为 `storyboard-v4`，视频为 `video-v3`：32镜正文，1920×1080、24fps、448.375秒、198条双语字幕。用户明确批准了V4分镜，以及 `outro-review-v1` 的字标和最后一镜预览；V3已交付并完成匿名整片下载校验。这些记录不等于用户已完整验收V3，也不等于代理实际听审。制作记录的 `actualListening=false` 保持原样。

## 1. 首镜要交代对象与因果，扩写不能只增加术语解释

第01镜初稿直接说诅咒“不肯把容器交给对方”，没有交代昴的处境、“容器”指谁，以及争夺为什么会阻止死亡。用户先要求扩展解释，第二轮仍指出“容器”像凭空冒出。

第一次修订补了背景，却又加上“这里说的‘容器’，就是承受诅咒的昴”。这让解说停下来解释一个观众本来不必先学的词，没有解决叙事顺序。最终V3、V4采用的说明顺序是：

1. 爆炸后，昴重伤昏迷。
2. 体内几股诅咒本来都会侵蚀他的性命，却不肯让别的诅咒先夺走这条命。
3. 相互争夺形成牵制，让他暂时活下来；重伤未愈，意识未恢复。

原著开头确实使用“容器”的比喻，但原文有这个词，不代表解说可以省略其指代和上下文。此次没有改动原著，只在解说中用具体人物和因果取代不必要的术语。黑色旋涡仍是主观意象，不能把画面演出反写成已查明的生理机制。

后续检查：把首镜单独读给不了解本节的人，确认能辨认“谁处于什么状态、什么在作用、为何出现这个结果”。需要保留术语时，在首次使用处说明指代；不需要时直接说具体对象。扩写之后仍要核对信息顺序，不能以字数增加代替解释清楚。

## 2. 耳光必须按三维动作核对，动作线救不了掌背错误

第22镜先后出现状态和角度奇怪、不够真实，以及用户明确指出的“左手正手打反手耳光”。早期描述只写“横掴、手掌击脸、顺势转头”，没有把出手侧、掌面、接触面、挥打路径和头部转向统一到同一个机位。补脸红、动态线和手指细节后，整体关系仍可能像推脸或抚脸。

最终采用侧面近景：雷姆在画面左，近侧解剖右臂出掌；昴在右，近侧为解剖左颊。镜头可见雷姆右手手背，掌面朝向昴左颊，取手指掠过、掌根开始离开的瞬间。挥打与昴头部小幅偏转都包含朝纵深的分量，不把脸直接翻到画面另一边。荷莉继续托抱，雷姆的腿不承重；动作镜保持稳定全幅。

这是一套本节调度，不是原著指定的出手侧，更不是“所有耳光都必须右手打左脸”的通用规则。有效的方法是逐项对照：

| 要素 | 必须能从原图判断的关系 |
| --- | --- |
| 手臂归属 | 从肩、肘、腕追到同一只手，拇指侧与掌背可见性一致 |
| 打击方式 | 正手或反手所需的掌面、挥打弧线与接触面成立，不能只靠提示词命名 |
| 动作瞬间 | 蓄势、接触或掠过三者明确，不把停留按脸画成高速掌击 |
| 受力反应 | 头颈和肩躯随力小幅转动，方向与机位、挥掌路径一致 |
| 身体限制 | 托抱支点、无力双腿与邻镜伤势保留，不因重画动作变成站立或换伤侧 |

原尺寸看动作链，再看脸、手和字幕空间。若旧构图持续迫使手掌、手腕和头部互相矛盾，应重选机位，不继续在错误接触关系上堆动态细节。最终采用项以图片哈希、分镜JSON及批准记录为准，不能凭某份旧提示词文件名判断。

## 3. 多音字按词义建表，修一个词不必重配整片

视频V1把“长回一只手”的“长”读成了 cháng，用户纠正为 zhǎng。原始无提示识别也出现“常回一只手”。已有“十米长”读 cháng 的经验不能覆盖生长义，不能把同一个汉字全局替换成一种读法。

V2保留字幕“长回一只手”，只在第10镜的TTS输入中将该词组映射为“掌回一只手”。使用冰糖默认声线和速度连续合成完整语义组，再在实测静音处裁出完整五字词组，替换原录音中的同长窗口。原API源和采用WAV分别保留哈希，补丁只用固定增益匹配，没有变速、移调、压缩或均衡。

此次补丁长1.08秒，全局范围为139.430–140.510秒；旁白及混音在补丁外的PCM保持一致。完整句仍落在原字幕窗内，因此只更新五字的实际对齐，不重排后续镜头和声音事件。新源、采用补丁和最终AAC都保留无提示识别结果；第二识别器也由“常”转为“掌”。这些是输入与辅助核验记录，不能写成人耳声调或自然度已经验收。

后续检查：在合成前把多音字连同完整词组和语义登记；同音别名只影响实际语音输入，不污染显示稿。修复后核完整音节、声尾、静音接点、字幕窗口和最终编码；没有安全接点或超窗时，按语义组处理，不能截尾或压缩语速。

制作中还发现第04镜的24kHz源在48kHz整数转换时出现一个满幅样本。采用浮点中间格式保留重采样过冲，后续以固定增益留余量；不把整数削波误判成原声问题，再用音色处理掩盖。

## 4. “Re:0风格”必须落实到资产、位置和入场方式

这次最明显的执行缺口是把风格要求当成几个形容词，没有落实到实际采用的字标和位置。视频可以解码、片尾没有黑闪，都不能证明片尾符合用户既定设计。

| 版本或反馈 | 问题与处理 |
| --- | --- |
| V1片头 | 普通粗体、粉色描边的“RE 0”和节名被用户指出难看。V2改为独立品牌字标，节号与节名分级排版，不把正文字幕样式直接放大当标题 |
| V1片尾 | 普通粗体描边的“未完待续”没有形成既定Re:0字标效果 |
| V2片尾 | 虽已换成冷白淡紫字标，仍自行改了字形和装饰，并放在左侧中部。用户再次指出原定位置是右下角、效果也不一致 |
| 实际定位 | 第三节参考素材在工作区缺失，但第一、二节仍有原始透明字标与时间线；后来找回后才恢复裂纹字、淡紫光晕、荆棘与叶片的具体参照 |
| 图审与V3 | 按找回的原版效果重新生成字标，先交付透明效果图和最后一镜右下角预览。用户明确确认后才替换视频片尾 |

有效检查应覆盖三项：具体字标的字形、纹理与装饰；在最后一镜中的相对位置、大小与留边；入场方式与末镜机位、亮度的连续性。只保留冷白淡紫颜色，不能称为恢复原版效果。

本节获确认的1080p参数为：左上角(1000,770)，尺寸820×274，右侧留100像素、底部留36像素，0.9秒淡入，不口播。后续默认沿用右下角与已确认的字标风格；具体坐标、尺寸和时长应结合画幅及主体适配，不把这些本节数值硬套到所有画面。

旧效果需要恢复时，先查采用清单、透明叠加资产和历史时间线；一个参考目录缺失，不等于只能凭描述另造。用户要求先审效果时，交付“效果单图＋最后一镜合成图”，批准绑定实际文件和布局，再渲染。没有新的图审要求、同范围已经获批时，直接复用，不增加例行确认。

V3从确认预览所用的无字末镜画面继续，采用同一透明字标和布局。实际查看首、中、末及淡入中点，并与最终编码抽帧对照；静态叠加区域外像素一致，不能将这一结论扩大为压缩视频逐像素一致。SSIM、亮度差和完整解码只能辅助核对，不能代替字形、位置和构图的实际查看。

## 5. 拟音与动效绑定事件，不靠数量证明表现力

用户要求丰富耳光、黑块破裂等声音，并加入流动黑雾。V1最终组织了45处拟音事件，以及黑雾、碎屑、火星和局部治愈光。这些数量只是本次清单，不是以后每集的指标，也不能据此称声音已经好听。

- 耳光区分挥臂声与一次掌击。先看动作所处瞬间，再核素材前导静音、真实起音与峰值；不能把文件开头直接当成接触点。本次掌击峰值对齐到297.96秒，具体值随本节时间线，不复用到别节。
- 黑壳破裂区分断裂瞬态与碎屑落下，按实际语义和画面顺序叠放；素材命名不等于已经同步。
- 黑雾沿现有意象流动，碎屑和治愈光按事件出现；不为增加动效重画获确认的耳光手势，也不添加新的伤势、攻击或剧情结果。
- 最终AAC真峰测得−2.48dBTP，综合响度−19.93LUFS。峰值约束优先，没有为追约−18LUFS而压缩或改变已确认声线。实际听感未由这些数值替代。

本片为了保护第14、15镜伤手，统一调整了整片双语字幕位置，并检查实际编码字形与留边。可复用的是“构图、运镜、正式文字一起检查”的方法，不能把本次下移60像素当成新默认，或宣称所有人物的每只手都完全无遮挡。

## 6. 局部返修用文件证据保留正确内容

V2只替换读音补丁和片头片尾；V3只替换4秒片尾，复用其余33个视频片段，并直接复制V2整条AAC音轨。终检证明前10,665个视频packet及全部21,019个音频packet的内容和相关时间保持一致，保留了读音修正、打耳光声、碎裂声和黑雾等既有内容。

后续可复用的方法是：画面或时间轴未影响音轨时优先复制音频流；音频小修时保留无关视频流。检查实际packet、时间戳和有效时长，不能只看到命令里写了 `copy` 就标为保留成功。冻结旧版不回写，候选、用户批准、采用版与完整成片验收分别登记。

本次脚本也出现过小型接口错误：FFmpeg的fade时长写成 `.08` 导致解析失败；记录字段名拼错导致输出阶段报错；QA约定的抽帧文件名与实际产物不一致。后续沿用已验证接口，时长写成 `0.08` 这类完整数值，核实际输出路径和阶段清单后再冻结。命令成功不代替质量通过；命令失败也不能跳过盘点实际产物就整批重做。

## 7. 交付核验和素材防重保持独立

V1、V2、V3分别上传、关闭发送页，用新匿名接收上下文下载解密整片并核SHA-256；V3接收字节与本地源一致。下载后同一页面曾仍显示100次，新匿名页显示99次；最终记录后者的实际显示，不把100次上限直接减一，也不把这种页面表现当成平台固定机制。期限写采集时间和预计到期，不伪称取得精确服务端时间。

上传沿用当前代理和CA校验，可用已验证的会话级转发，不修改永久信任、不关闭TLS验证。浏览器出现连接错误时按具体请求排查，最终以云上传完成和独立接收文件为准。

发布素材包恰好三文件，V1已取得Gmail接受和发送读回记录。后两次只改视频，包内封面、标题、简介和tags未变，因此按包哈希复用，未重复寄。此次整理经验同样不触发视频重制、链接重传或素材重发。

## 9. 运镜参数存在，不等于播放时有运动感

用户在V3交付后反馈，观看时像静态画面。检查实际采用时间线和渲染器后，问题可落实为：32个正文分镜中，16个固定机位，合计220.25秒；另16个都在约11.71–20.50秒内仅从1.00倍放大到1.03倍。程序根据描述是否以“稳定”开头二选一，没有为普通镜头配置独立焦点和横纵移动，所有推进都围绕画幅中心。

3%的推进在1080p下，靠左右边缘的细节整镜也只移动约28像素，靠近中心的人脸位移更小。镜头停留十几秒，人物和背景又一起缓慢等比放大，运动很难被明显感知。保护伤手、托抱关系和接触点的出发点合理，但不能因此把过多镜头一律固定，再用同一个微幅居中缩放覆盖其余镜头。

本次从最终V3视频抽取第02、09、22、32镜的首末帧，在排除底部字幕的区域做缩放拟合：第09、32镜最接近1.03倍，第02、22镜为1.00倍。抽查确认微幅推进确实进入了成片；它没有证明整片连续观看时的运动感合格。之前只看参数与首中末，缺少连续播放的感知检查，是本次设计和验收的缺口。

后续应按叙事焦点逐镜设计方向、起终点、幅度和停留时间。普通叙述镜可以推进或缓慢横移，关键伤手、掌击等镜头有依据地保持稳定；不把“全部都动”或“统一增加一个百分比”当成修法。先连续预览代表镜头，确认运动能被感知且不裁关键部位，再用于同条件镜头。字幕或黑雾在动，也不能代替相机运动的验收。

这次只完成诊断与经验补充，没有重渲染视频，也没有更改音轨、时间线或原有批准记录。
